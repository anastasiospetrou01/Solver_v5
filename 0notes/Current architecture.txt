Project: Solver_v5 — Research and implementation of a robust scalable iterative/multigrid linear solver

Act as an expert in computational fluid dynamics, finite-volume methods, saddle-point systems, PETSc, MPI, Krylov methods, algebraic multigrid, block preconditioning, and high-performance scientific computing.

I am developing Solver_v5, a custom 2D steady incompressible finite-volume CFD solver. The current solver is numerically robust and distributed across MPI ranks, but its production linear solver is a parallel sparse direct LU solve using PETSc + MUMPS.

The objective of this work is to determine, through proper research and controlled experimentation, how to formulate a robust and genuinely scalable iterative/multigrid linear solver for Solver_v5.

Do not assume that AMG or an iterative solver must automatically be faster than MUMPS. So far, that has not been true for the problem sizes we have tested. The objective is to determine:

what iterative formulation is mathematically appropriate for this solver;
why our previous iterative attempts were not sufficiently robust;
at what problem size the direct solver becomes inferior;
how to construct an iterative method that remains robust as mesh size, Reynolds/Rayleigh number and processor count increase;
whether multigrid should be applied directly to the monolithic system or, more likely, inside a physically meaningful block preconditioner.
Current solver architecture

The current solver has the following important characteristics:

2D finite-volume method.
Structured Cartesian grid.
Collocated variables.
Steady incompressible Navier–Stokes equations.
Fully coupled u–v–p linear system.
Rhie–Chow-type pressure–velocity coupling.
Energy equation solved separately when enabled.
Boussinesq buoyancy is available.
First-order upwind and blended second-order upwind convection.
Under-relaxed nonlinear outer iterations.
Distributed-memory MPI implementation.
Structured y-slab domain decomposition.
Local fields plus halo/ghost exchange.
Halo width = 2.
Local equation assembly on each rank.
Distributed PETSc matrices/vectors.
Fixed PETSc COO sparsity structure with numerical values updated each nonlinear iteration.
Numba-compiled CFD kernels.
Global fields are not gathered every nonlinear iteration.
MPI-MAX profiling is available.

Current flow DOF ordering is:

[u0, v0, p0, u1, v1, p1, ...]

The current production linear backend is approximately:

PETSc KSP
    preonly
       ↓
PETSc PC
       lu
       ↓
MUMPS

MUMPS must remain available permanently as:

a reference solver;
a regression baseline;
a robust small/medium-problem solver;
a debugging/fallback solver;
a means of verifying iterative solutions.

Do not remove or weaken the direct solver while developing the iterative solver.

Current performance baseline

A representative benchmark is the differentially heated 400 × 400 cavity:

cells            = 160,000
coupled flow DOF = 480,000
nonlinear iterations = 92

The direct method converges very reliably.

On an Intel Xeon w5-3535X:

8 MPI ranks   → 71.07 s
20 MPI ranks  → 54.70 s
30 MPI ranks  → 44.68 s
40 MPI ranks  → 56.99 s

Thus the current direct solver is still remarkably competitive at this problem size.

Numerically, changing MPI rank count does not change the converged solution to the reported precision.

Therefore, do not judge an iterative implementation as successful merely because it converges. It must eventually demonstrate a meaningful advantage in:

runtime;
memory;
scaling;
or maximum solvable problem size.
Previous iterative work

We have previously experimented with approaches involving PETSc Krylov methods, field splitting, Schur-complement ideas, PCD-type preconditioning, GAMG/HYPRE and related configurations.

Some configurations could solve selected cases, but none became sufficiently robust and generally superior to the direct MUMPS implementation.

Typical problems included some combination of:

poor convergence for harder CFD cases;
strong sensitivity to preconditioner configuration;
pressure-block difficulties;
nullspace issues;
poor nonlinear robustness;
more linear iterations than expected;
iterative solve time failing to beat direct LU;
configurations that worked on the cavity but failed on obstacle/wake cases;
insufficient scalability or excessive setup cost.

Do not simply recreate these old attempts.

We need to understand mathematically and computationally why they behaved that way.

Stage 3 — Formulate the block system explicitly

Starting from the matrix that the code actually builds, express the system in block form.

For example, determine whether it can appropriately be interpreted as something similar to:

$$ \begin{bmatrix} A_u & A_{uv} & G_x \\ A_{vu} & A_v & G_y \\ D_x & D_y & C \end{bmatrix} \begin{bmatrix} \delta u\\ \delta v\\ \delta p \end{bmatrix} = \begin{bmatrix} r_u\\ r_v\\ r_c \end{bmatrix} $$

but derive the actual structure from Solver_v5.

Then derive the corresponding Schur-complement structure and identify which terms can practically be approximated.

I want the preconditioner to follow from this analysis rather than from PETSc option experimentation.
